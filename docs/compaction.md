# 上下文压缩

CoilCoil 自己负责「压缩的内容」，Pi 负责「什么时候压、从哪儿切、写进会话」。
代码：`packages/workflow/extensions/compaction.ts`（入口）和 `packages/workflow/extensions/compaction/`。
2026-09-28 定稿，取代了此前打在 Pi 源码里的压缩补丁（见 `docs/pi-upstream.md`）。

## 目标

**压缩次数尽量少。** 每压一次，缓存就断一次，模型也会丢掉一些细节；压一次就要留出足够的空间。

## 分工

| 谁 | 管什么 |
|---|---|
| Pi | 触发（上下文超过「窗口 − 预留量」、模型报超长、手动 /compact）；保留最近约 2 万 token 原样不动（`keepRecentTokens`，切在消息边界，不拆开工具调用和结果）；把结果写进会话；压完重试这一轮 |
| CoilCoil 压缩扩展 | 保留区之外那段历史变成什么（第 1 层 / 第 2 层） |
| context-transcript 扩展 | 把被压掉的原文存成纯文字存档，放在会话文件旁边；系统提示从第一轮起只给稳定路径，分段索引需要时从存档读取，避免每次压缩后改写系统提示 |
| 运行时（runtime-core） | 把压缩扩展报上来的每一步写进 `runtime-*.jsonl`（`coilcoil_*` 事件）；失败时用真实原因提示用户 |

原始会话文件从不修改：压缩只是在当前这条线上追加一条压缩记录，模型看到的是「最新摘要 + 切点之后的原文」。

## 两层

**第 1 层：整理稿（不调模型）**
- 保留区之外：用户和助手的原话一字不动；删掉思考过程；工具调用只留一行痕迹（短参数原样，大段参数只留开头和总长）；工具结果只留长度，出错时留开头一段报错。
- 上一次压缩如果也是整理稿，接在前面；如果是模型写的摘要，放在「更早内容的摘要」下面。末尾附改过、读过的文件清单。
- 估算压完的总量 = 系统提示和工具说明 + 整理稿 + 保留区。**≤ 窗口的 35%** 才采用，否则整份作废、走第 2 层。
- 手动 /compact 写了额外要求时直接走第 2 层（用户要的是模型写的摘要）。

**第 2 层：交接摘要（调模型）**
- 同账号、同模型的 Claude 请求仍在缓存有效期内，且支持逐消息思考级别时，优先复用刚刚实际发送的系统提示、工具和消息前缀，只追加摘要指令。通过主请求的真实 usage 留出摘要空间，不重新拼一份相似但无法命中的历史。摘要沿用主会话的已配置 provider 路径，保留订阅别名的模型及历史消息转换。
- 缓存过期、切换模型/账号、空间不足或请求格式不兼容时，回到下面的文本摘要路径。冷会话不会为了赌缓存而重读一整份长历史。
- 材料：删掉思考过程，工具调用和结果都留（很长的结果留头尾）。
- 一次装得下（材料 ≤ 模型窗口的一半，且不超过 12 万 token），就一次写完，在上一份摘要的基础上更新。
- 装不下（历史太长，或者从大窗口模型切到了小窗口模型），就按时间切块，**各块同时写**，再用一次请求**合成一份**。某一块模型说太长，就对半切开重来。
- 摘要按固定小节写：目标、约束与偏好、已完成、**进行中（执行到哪一步）**、关键决定与踩过的坑、下一步、关键上下文（路径、报错原文、对用户的承诺）。中文书写，技术标识保留原文。
- 请求：**低思考**；发出后 3 分钟没有任何返回、或中途 90 秒不动，就断开重试；临时错误退避重试，最多 3 次。
- SDK 内层重试关闭，由摘要层统一控制；认证错误和无效请求不重复提交。摘要 usage 保留实际缓存读取、写入和成本。
- 模型用设置里的「上下文总结」模型，没设就用会话当前的模型。

**失败**
- 第 2 层失败就明确取消，会话保持原样，提示用户真实原因。不交回空结果——那样 Pi 会拿原始历史自己再压一遍，超大会话必然 400。
- 同一处刚失败过，10 分钟内自动压缩不再重试（手动 /compact 不受限）。
- 压完估计仍超过自动压缩线（窗口太小，或保留区本身太大），也算失败，不落一个马上又要压的结果。

## 数字从哪来

- token 估算：中日韩字符按 1 个 token，其余按 4 个字符 1 个。Pi 的「字符 ÷ 4」对中文少估三四倍。
- 实测（2026-09-28，会话 A，压缩前约 149 万 token、原始记录约 1200 万字符）：按它自己的 50 万窗口，第 1 层压完约 8 万 token（16%），不调模型，1 秒多；假设窗口只有 20 万时走第 2 层，分 3 块同时写再合并，共 113 秒。旧的逐段串行、开着最高思考的做法用了 39 分钟。

## 日志

`agent/logs/runtime-*.jsonl` 和已归档的 `.jsonl.gz` 中，scope 为 `compaction`、事件名以 `coilcoil_` 开头：
`layer1_planned`（估算和决定）、`layer2_started`、`chunked`、`request_started` / `request_completed`（每次请求耗时）、`request_stalled` / `request_retry`、`done`、`failed`、`skipped`。每条都带会话路径。

`cache_prefix` 记录这次是否能复用主会话缓存，`prefix_fallback` 记录回退原因，`request_usage` 记录摘要每次请求的普通输入、输出、缓存读取和写入。

## 主会话缓存

运行时在 Pi 的请求包装器之前应用缓存策略：Claude 订阅主会话默认一小时，API key 保留服务商默认值；请求选项或 `PI_CACHE_RETENTION` 的 `short` / `long` / `none` 显式设置优先。缓存保活与真实请求使用同一个有效期。后台记忆和子 Agent 使用各自原有策略。

`runtime-bridge` 在首次发送前保存最终系统提示快照，由会话统一持有，包含初始记忆、Skills、存档查询路径和其他提示层。后续轮次、资源重新加载、压缩及重开同一分支都复用这份快照。快照带会话 ID，新建或复制成新会话时读取新的资料。

会话开始后，后台记忆整理、磁盘文件和全局配置修改不会重新注入当前对话，也不再追加隐式记忆更新消息。后台资源热重载及当前会话的系统提示、Skill 开关在运行期间锁定；修改在新对话生效。用户明确增删或修改 MCP 工具仍会在会话空闲后重载，并记录 `user_tools_changed`，其可能导致的缓存重建属于预期变化。首次发送之前仍可配置会话。正常压缩允许重建历史投影，用户主动回溯则恢复所选分支；两者保留原有功能，压缩不会刷新系统提示快照。

### 断点规划与缓存账本

`extensions/cache/` 在 provider 完成历史、账号别名和工具转换之后，对最终请求体规划断点。默认策略在工具末尾和系统末尾各保留一个稳定断点，消息最多两个：有完整前缀 usage 支持的父边界，以及本次会话尾部。总数不超过四个；deferred 工具占位符不会取代原有普通工具断点。服务商不支持工具标记或一小时 TTL 时遵循其兼容性配置，显式关闭缓存时不加任何标记。请求已经配置混合 TTL、scope 或顶层自动缓存时，保留原配置，不擅自重排或统一升为一小时。

父边界按保留 JSON 字段顺序的完整前缀哈希匹配，并检查有效期，不能拿 UI 消息下标直接定位。消息一次增长超过服务端 20 个位置的回看窗口时，显式父断点仍提供查找入口。共享压缩摘要不在一次性摘要指令后写缓存；发送前核对转换后的父前缀和实际 HTTP 路由／beta 等请求头，不匹配时在发 HTTP 前拒绝并回退独立文本摘要，不按网络错误重试。不能安全重放的调用方自有混合／scope 策略也采用独立摘要。Pi 回溯分支总结仍走独立请求，不应把记录到它的 usage 误称为已实现 Claude 的父前缀共享。摘要（包括冷回退、分块）计入同一账本，但不替换主会话的比较基线。

账本持久化为 `coilcoil-prompt-cache-v1` 自定义条目，不进入模型历史。内存保留最近 40 次请求和最多 32 个消息断点；每次仅保存累计计数、本条记录、最近少量断点和主基线，恢复时合并检查点，避免每轮重复写入整段滚动历史。不保存提示正文、工具参数或凭证。日志写入 `cache/request`，运行时面板展示主会话及总结请求的读取、写入、5 分钟／1 小时写入细分和失效归因。累计比例仍为 `read / (ordinary + read + write)`，正常增长的新尾部写入不会被单独认定为失效。保活和命名请求不属于本面板的请求集合。

显著下降采用与参照实现一致的容差：相对前后较小输入，少读至少 2000 token 且低于 95%。首次写入、预期压缩、用户回溯和用户修改工具分别记录；未找到结构变化或过期证据时保留 `unknown`，不把猜测当成服务端原因。有效期、指纹和 `parentPinned` 都是客户端依据，不保证服务端此刻仍有缓存。

缓存计时从请求准备／HTTP 发出时开始，不从首 token 到达或输出结束开始。仅头部命中不会建立完整会话边界；默认尾断点必须覆盖到消息末尾，且普通输入不超过 16 token 的协议收尾余量，才推定整段前缀有 usage 支持。辅助请求只有读写量足以覆盖已知父边界时才续记它的时间。这仍是保守推断，并非服务端逐断点存活查询。

官方 Claude API 的 API key 主通道额外请求 cache diagnostics，并沿用上次主响应 ID；订阅和未确认能力的通道默认仅做本地指纹诊断。响应提供差异原因时单独保存。若官方接口明确以 400 拒绝可选 diagnostics 字段，移除该字段重试一次，并在当前会话停用它；其他请求错误、认证或限流不走这条降级。自定义 endpoint 不自动假定支持此能力。

### 工具与文件上下文稳定性

`goal_complete` 的 schema 在会话内保持可用，由执行函数检查当前是否有目标，完成或暂停目标不再增删工具。MCP 发现不阻塞首轮：已经就绪的直接工具进入初始清单，首轮开始后或扩展关闭后才到达的结果不再回填；未提供直接定义的工具仍可经通用 `mcp` 工具访问。首次请求保存完整直接工具定义、顺序和激活名单，普通重载和恢复重放快照。用户主动修改 MCP 和调用目的审计设置写入刷新标记，等模型运行、压缩及子代理结束后更新工具；后台刷新不会取消已排队的用户修改。子会话同样持久化系统提示和 MCP 快照。

`read-cache` 在主会话和子会话中对重复 Read 正文去重。它核对实际返回内容、同一路径与读取范围，以及原始完整结果是否仍存在于最终上下文；一致且原结果字节数超过提示两倍时才追加简短引用，短文件保留原文。文件变化、不同范围、截断、图片、错误、压缩或清理移除了原结果时返回正文。实际 Read 仍执行，因此外部编辑不会被 mtime 假象遮住；此优化减少入模正文，不承诺消除文件 I/O，也不改写旧工具结果。

保活继续使用 Pi 原有受模式、经济性和安全窗口约束的模型重放机制，并沿用真实请求的有效期；重放会产生 API 用量，与参照安装中受账号和远程开关限制的 request-ID-only cache touch 不等价。本轮没有额外开启更频繁的保活。完整的订阅 overage／远程 allowlist／活跃 5m 延续决策以及静态 system 的受限 global 分区仍未移植。新版真实命中率和 API 等价节省需上线 usage 验证，离线回归不代表服务端缓存实验。逐项差异见 [本轮审核](claude-code-cache/suocode-audit.md)。
